## 1. Architecture Overview

```
┌─────────────────┐        REST/JSON        ┌──────────────────┐
│   Next.js App    │ <────────────────────> │   FastAPI Server  │
│  (App Router)     │      JWT in header      │                    │
│  - Pages/Forms     │                         │  - Routers         │
│  - Zustand/Context │                         │  - Services (logic)│
│  - Axios/fetch      │                         │  - SQLAlchemy ORM  │
└─────────────────┘                         └────────┬──────────┘
                                                         │
                                                 ┌───────▼────────┐
                                                 │  PostgreSQL DB  │
                                                 └─────────────────┘
```

Follow a **service-layer pattern** on the backend (same shape you used on TransitOps): routers stay thin, all business logic (ledger posting, invoice conversion, budget validation, report computation) lives in `services/*.py`. This is what makes the P&L/Balance Sheet logic testable independent of HTTP.

## 3. Document Status Workflow (from the mockup — this is the actual state machine to implement)

The mockup shows every transactional document (PO, Vendor Bill, SO, Customer Invoice, Payment, Budget) follows the same **New → Confirm → (Post/Pay)** pattern with a consistent button row: `New | Confirm | Cancel | Back`, and Budget additionally has `Revise`.

| Status | Meaning | Triggering action |
|---|---|---|
| Draft | Editable, no accounting impact | `New` |
| Confirmed | Locked, journal entry posted | `Confirm` |
| Cancelled | Void, no accounting impact | `Cancel` (only from Draft/Confirmed) |
| Revised (Budget only) | New version created, links back to original via "Revised With" | `Revise` (only from Confirmed) |

**Implement this as a single reusable state-machine mixin/service** (`document_state.py`) rather than duplicating status logic per document type — PO, Bill, SO, Invoice, and Payment all transition the same way. Payment has one extra pair: `Post` / `Reset to Draft`.

## 4. Core Business Logic (the part that actually needs design, not just CRUD)

### 3.1 Double-Entry Journal Engine
This is the heart of the system — everything else just *calls* it.

- A `JournalEntry` is never created directly by a user; it's always generated by the service layer as a side-effect of a business event (bill posted, invoice posted, payment made).
- **Invariant to enforce in code:** `sum(debit) == sum(credit)` for every journal entry. Reject/raise if unbalanced — this is your main "correctness" guard for the demo.
- Suggested helper: `post_journal_entry(journal_id, date, reference, lines: list[{account_id, debit, credit}])` used internally by every other service.

**Standard postings to hard-code:**
| Event | Debit | Credit |
|---|---|---|
| Vendor Bill posted | Purchase Expense | Creditors (Accounts Payable) |
| Payment made to vendor | Creditors | Bank/Cash |
| Customer Invoice posted | Debtors (Accounts Receivable) | Sales Income |
| Payment received from customer | Bank/Cash | Debtors |

### 3.2 Purchase Flow (PO → Bill → Payment) — matches mockup exactly
1. **Purchase Order**: `New → Confirm → Create Bill`. Lines: Product, Budget Analytics (link to an Analytic Account, many-to-one), Qty, Unit Price, Total (Qty × Price, auto-computed).
2. **Budget check on Confirm**: if the PO total pushes the linked analytic account's committed spend over its *approved* budget amount, show a **blocking warning** ("The entered amount is higher than the budget amount for this line. Consider adjusting the value or revise the budget") — this is a real validation rule from the spec, not decorative.
3. `Create Bill` button on the confirmed PO → generates a **Vendor Bill** pre-filled from the PO (vendor, lines, budget analytics, purchase account defaulted). Bill shows both `PO` and `Budget` reference badges and links back to the source PO ("only show if Bill created from PO / hide if Bill created fresh without PO").
4. **Vendor Bill fields**: Vendor Bill No., Bill Reference, Bill Date, Due Date, lines with `Product | Chart of Account (defaults to Purchase) | Budget Analytics | Qty | Unit Price | Total`, footer shows `Paid Via Cash / Paid Via Bank / Amount Due`.
5. On **Confirm**, the same budget-exceeded blocking check runs again against the Bill total, and — critically — **a journal entry is posted automatically**: Dr Purchase Expense / Cr Creditors. This is not a separate manual step; confirming *is* what posts it.
6. `Pay` button opens a **Bill Payment** screen: `Post | Reset to Draft | Back`, fields `Accounting Date`, `Journal`, and an `Account | Partner | Debit | Credit` grid (Dr Creditors / Cr Bank or Cash). Posting reduces `Amount Due` on the bill.

### 3.3 Sales Flow (SO → Invoice → Payment) — mirror of purchase flow
1. **Sales Order**: `New → Confirm → Create Invoice`. Lines: Product, Budget Analytics, Qty, Unit Price, Total.
2. `Create Invoice` → **Customer Invoice** pre-filled from SO, with `Invoice Reference`, Invoice Date, Due Date, same line structure (Product | Chart of Account defaults to Sales | Budget Analytics | Qty | Unit Price | Total), footer `Paid Via Cash / Paid Via Bank / Amount Due`.
3. Confirming the invoice **auto-posts** the journal entry: Dr Debtors / Cr Sales Income.
4. `Pay` opens **Invoice Payment**: `Payment Type: Send / Receive`, `Partner`, `Payment Via`, `Amount`, `Note`, then `Confirm | Cancel`.

> The spec's tax field on SO lines is present in the mockup as a column but not elaborated in the field-computation notes — treat it as a stretch goal (split to a `Tax Payable` account) and don't let it block the core demo.

### 3.4 Budget — field computations (straight from the mockup's "Field Explanation" box)
This is more precisely specified than the PDF alone suggests, so build it exactly like this:
- **Committed Amount**: monetary, entered by the user when creating the budget.
- **Achieved Amount**: *not* entered — computed by searching Analytics tagged on **Sales Invoices** (type Income) and **Vendor Bills** (type Expenses) whose date falls in the budget period, summing their totals.
- **Achieved %** = `(Achieved Amount / Committed Amount) * 100`.
- **Amount to Achieve** = `Committed Amount − Achieved Amount`.
- Budget states: `Draft → Confirm → Revise` (creates a new budget row referencing the original via "Revised With", original stays as history) `→ Cancelled`.
- **Budget Report**: List view (Name, Start/End Date, Status, % chart) and a **Kanban view** with a donut chart per budget showing Achieved vs Balance — this is a visual the frontend should actually build (recharts pie chart), not just a table.

### 3.5 Ledger Balance Computation
For any account, balance = `sum(debit) - sum(credit)` (for Asset/Expense) or `sum(credit) - sum(debit)` (for Liability/Income/Capital), summed across all `journal_items` where `account_id` matches. Build this as one reusable query/service function — every report calls it.

### 3.6 Report Generation
Field computations, taken directly from the mockup's report notes:
- **P&L:** `Income = Total of Income accounts`, `Expenses = Total of Expense accounts`, `Net Income = Income − Expenses`. Layout: Income block (with Sales-type income lines), Expenses block (Purchase Expense, Other Expense), Net Income total. Filter by year, `Print` action.
- **Balance Sheet:** two columns, **Assets** (Bank, Cash, Debtors) and **Liabilities** (Capital, Creditors), each summed to `Total Asset` / `Total Liability`. Account-to-column mapping note from the mockup: *Bank/Cash/Debtors → Asset column; Creditors → Liability column; Capital → Capital column shown under Liabilities.* Sanity check for the demo: `Total Asset == Total Liability` — if it doesn't match, something posted wrong.

### 3.7 RBAC
Three roles gate at the router level (FastAPI dependency, e.g. `require_role("admin", "invoicing_user")`):
- **Admin** — full CRUD on master data + transactions + reports.
- **Invoicing User** — create master data, record transactions, view reports (no user/role management).
- **Contact** — read-only on *their own* invoices/bills (`WHERE contact_id == current_user.contact_id`) + can make a payment against their own bill/invoice.

## 6. API Surface (backend dev builds these; frontend dev consumes them)

```
POST   /auth/login                          → JWT
POST   /auth/register

GET/POST/PUT   /contacts
GET/POST/PUT   /products
GET/POST/PUT   /accounts
GET/POST        /journals

POST   /purchase-orders
POST   /purchase-orders/{id}/confirm        → runs budget check, may return 409 blocking warning
POST   /purchase-orders/{id}/create-bill    → "Create Bill" button
GET    /vendor-bills
POST   /vendor-bills/{id}/confirm           → runs budget check + auto-posts journal entry
POST   /vendor-bills/{id}/pay               → Bill Payment "Post"

POST   /sales-orders
POST   /sales-orders/{id}/confirm
POST   /sales-orders/{id}/create-invoice    → "Create Invoice" button
GET    /customer-invoices
POST   /customer-invoices/{id}/confirm      → auto-posts journal entry
POST   /customer-invoices/{id}/pay          → Invoice Payment (Send/Receive)

GET    /reports/balance-sheet?year=
GET    /reports/profit-and-loss?year=
GET    /reports/budget?period=              → list + kanban (achieved %, achieved amount, balance)

GET/POST /budgets
POST   /budgets/{id}/confirm
POST   /budgets/{id}/revise                 → creates new budget, sets revised_from_id
GET/POST /analytic-accounts
```

Agree on this contract **first**, before either of you writes a line of feature code — it's what lets you work in parallel without blocking each other.
